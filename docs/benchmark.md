# 성능 측정

`scripts/benchmark.py`로 측정한 결과입니다. 순수 파이썬 구현이라 절대 수치보다는 **데이터가 늘 때 어떤 지표가 어떻게 변하는지**를 보는 용도입니다.

```bash
python scripts/benchmark.py          # 1천 / 1만 / 10만 건
python scripts/benchmark.py 300000   # 크기 추가
```

## 결과

측정 환경: Python 3.13 / Linux (클라우드 컨테이너, 단일 실행)

| N | SET ops/s | max SET ms | GET ops/s | resize | capacity | max chain | avg chain | KEYS ms | expire-all ms | SET+LRU ops/s | evicted |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1000 | 86863 | 2.5 | 481121 | 8 | 2048 | 3 | 1.21 | 0.6 | 17.7 | 95359 | 885 |
| 10000 | 89355 | 17.6 | 301946 | 11 | 16384 | 7 | 1.45 | 9.5 | 259.2 | 89188 | 8929 |
| 100000 | 52350 | 621.2 | 331504 | 15 | 262144 | 5 | 1.27 | 89.0 | 3031.6 | 63897 | 90000 |

| 컬럼 | 의미 |
| --- | --- |
| max SET ms | 가장 느렸던 SET 한 번. 리사이즈(전체 재해싱)가 일어난 순간의 지연 |
| resize / capacity | 해시맵 확장 횟수와 최종 버킷 수 (8에서 시작해 2배씩) |
| max / avg chain | 최장 체인 길이와 사용 중인 버킷의 평균 체인 길이 |
| expire-all ms | N개 키가 동시에 만료됐을 때 한 번의 active expiration에 걸린 시간 |
| SET+LRU | maxmemory를 데이터의 약 10% 크기로 걸고 SET할 때 처리량 (매번 LRU 제거 발생) |

## 해석

1. **GET은 데이터가 100배 늘어도 처리량이 비슷합니다.** 해시 조회 + 리스트 이동이 모두 O(1)이기 때문입니다.
2. **체인 길이가 짧게 유지됩니다.** 로드 팩터 0.75 상한 덕분에 10만 건에서도 평균 체인 길이 약 1.3, 최장 5입니다. FNV-1a가 `user:0` ~ `user:99999`처럼 비슷한 키를 고르게 흩뜨린다는 근거입니다.
3. **리사이즈 순간 지연이 가장 큰 병목입니다.** 10만 건 규모에서 마지막 확장(131,072 → 262,144 버킷) 때 SET 한 번이 약 0.6초 걸렸습니다. 평균 처리량은 괜찮아도 특정 요청 하나가 멈추는 tail latency 문제입니다. → 점진적 리해싱으로 개선 가능
4. **동시 만료는 O(k log n)으로 커집니다.** 10만 개가 한꺼번에 만료되면 그 명령 하나가 3초가량 걸립니다. → 한 번에 처리할 만료 개수에 상한을 두는 방식으로 개선 가능
5. **LRU 제거가 있어도 SET 처리량이 크게 떨어지지 않습니다.** 제거 한 번이 O(1)이기 때문입니다.
6. **KEYS는 O(n)입니다.** 10만 건에서 약 90ms로, 데이터가 커질수록 선형으로 늘어납니다. → `SCAN` 방식으로 개선 가능
