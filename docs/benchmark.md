# 성능 측정

`scripts/benchmark.py`로 측정한 결과입니다. 순수 파이썬 구현이라 절대 수치보다는 **데이터가 늘 때 어떤 지표가 어떻게 변하는지**를 보는 용도입니다.

```bash
python scripts/benchmark.py          # 1천 / 1만 / 10만 건
python scripts/benchmark.py 300000   # 크기 추가
```

## 결과

측정 환경: Python 3.13 / Linux (클라우드 컨테이너, 단일 실행)

| N | SET ops/s | max SET ms | GET ops/s | resize | capacity | max chain | avg chain | KEYS ms | expire-all ms | SET+LRU ops/s | evicted |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1000 | 86863 | 2.5 | 481121 | 8 | 2048 | 3 | 1.21 | 0.6 | 17.7 | 95359 | 885 |
| 10000 | 89355 | 17.6 | 301946 | 11 | 16384 | 7 | 1.45 | 9.5 | 259.2 | 89188 | 8929 |
| 100000 | 52350 | 621.2 | 331504 | 15 | 262144 | 5 | 1.27 | 89.0 | 3031.6 | 63897 | 90000 |

| 컬럼 | 의미 |
| --- | --- |
| max SET ms | 가장 느렸던 SET 한 번. 리사이즈(전체 재해싱)가 일어난 순간의 지연 |
| resize / capacity | 해시맵 확장 횟수와 최종 버킷 수 (8에서 시작해 2배씩) |
| max / avg chain | 최장 체인 길이와 사용 중인 버킷의 평균 체인 길이 |
| expire-all ms | N개 키가 동시에 만료됐을 때 한 번의 active expiration에 걸린 시간 |
| SET+LRU | maxmemory를 데이터의 약 10% 크기로 걸고 SET할 때 처리량 (매번 LRU 제거 발생) |

## 해석

1. **GET은 데이터가 100배 늘어도 처리량이 비슷합니다.** 해시 조회 + 리스트 이동이 모두 O(1)이기 때문입니다.
2. **체인 길이가 짧게 유지됩니다.** 로드 팩터 0.75 상한 덕분에 10만 건에서도 평균 체인 길이 약 1.3, 최장 5입니다. FNV-1a가 `user:0` ~ `user:99999`처럼 비슷한 키를 고르게 흩뜨린다는 근거입니다.
3. **리사이즈 순간 지연이 가장 큰 병목입니다.** 10만 건 규모에서 마지막 확장(131,072 → 262,144 버킷) 때 SET 한 번이 약 0.6초 걸렸습니다. 평균 처리량은 괜찮아도 특정 요청 하나가 멈추는 tail latency 문제입니다. → 점진적 리해싱으로 개선 가능
4. **동시 만료는 O(k log n)으로 커집니다.** 10만 개가 한꺼번에 만료되면 그 명령 하나가 3초가량 걸립니다. → 한 번에 처리할 만료 개수에 상한을 두는 방식으로 개선 가능
5. **LRU 제거가 있어도 SET 처리량이 크게 떨어지지 않습니다.** 제거 한 번이 O(1)이기 때문입니다.
6. **KEYS는 O(n)입니다.** 10만 건에서 약 90ms로, 데이터가 커질수록 선형으로 늘어납니다. → `SCAN` 방식으로 개선 가능

이 결과는 [`checklist.md` 4-2](checklist.md#4-2-데이터가-10만-건으로-늘면-병목은-어디이고-어떻게-개선하는가) 답변의 근거입니다.

## 10만 건 규모 병목 분석

위 표는 "데이터가 늘 때 어떤 지표가 커지는가"를 보여 줍니다. 이 절은 10만 건에서 **시간과 메모리가 정확히 어디에 쓰이는지**를 단계별로 나눠 재고, 병목마다 대책을 정리합니다.

```bash
python3 scripts/profile_100k.py         # 단계별 시간 (N = 100,000)
python3 scripts/memory_overhead.py      # 엔트리당 실제 메모리
```

측정 환경: Python 3.14.4 / Linux (로컬, 단일 실행), 2026-11-09. 위 결과 표와 환경이 달라 절대값은 다릅니다.

### 병목과 원인

| 병목 | 측정 근거 | 원인 | 대책 |
| --- | --- | --- | --- |
| **해시 계산 (CPU)** | FNV-1a 키 10바이트 1.2µs, 64바이트 6.6µs. GET 한 번(2.0µs)의 절반 이상 | 순수 파이썬이 바이트마다 XOR·곱셈·마스크를 반복. 키 길이에 비례 | 키를 짧게 설계. 실무라면 C 확장이나 내장 해시. 해시값을 키 객체와 함께 캐시 |
| **리사이즈 순간 지연** | 마지막 확장 한 번이 298 ms, 리사이즈가 SET 전체 시간의 44% | 로드 팩터 0.75를 넘는 순간 모든 키를 한 번에 재해싱 (키당 약 3µs) | 점진적 리해싱, 예상 크기로 미리 할당, 샤딩 (→ [design.md 리해시 비용과 대안](design.md#리해시-비용과-대안)) |
| **대량 동시 만료** | 10만 개가 같은 시각에 만료되면 그다음 명령 하나가 2초 | active 만료가 만료된 키 k개를 한 명령 안에서 끝까지 처리, O(k log n) | 한 번에 처리할 개수·시간에 상한, 나머지는 다음 명령 (Redis active expire cycle: TTL 키를 20개씩 샘플링해 만료 비율이 높으면 반복하되, 한 번에 쓰는 CPU 시간에 상한) |
| **KEYS 출력 (I/O)** | 수집 60 ms인데 출력 문자열 만들기 467 ms (약 8배), 결과 2 MB | 키마다 `1) "…"` 줄을 만들고 따옴표·이스케이프 처리. 터미널이라면 2 MB를 그리는 시간이 더 붙음 | 커서 기반 `SCAN cursor COUNT n`으로 나눠 반환, 출력 버퍼링·배치 |
| **메모리** | 자료구조만 엔트리당 약 575~594 B, 10만 건에 약 58 MB. `memory_overhead.py`(값 `value-{i}`)에서 미션 공식 `used_memory` 2.08 MB의 약 28배 (키·값 문자열 객체까지 넣으면 33배) | 키 하나에 객체 4개 + 버킷 리스트·센티널 | 근사 LRU로 LRU 노드 제거, 단일 연결 체인/오픈 어드레싱 (→ [design.md 체인 노드 비용](design.md#체인-노드의-생성해제-비용과-재사용)) |
| **병렬성 없음** | CPU 코어 하나만 사용 | 단일 스레드 REPL + CPython GIL. 스레드를 늘려도 파이썬 코드는 동시에 실행되지 않음 | 프로세스 단위 샤딩 (아래). 정확성 문제는 [design.md 동시성 한계](design.md#동시성에서의-o1-보장-한계) |

GET이 10만 건에서도 2µs인 것처럼 **한 키를 다루는 연산은 규모와 무관합니다.** 병목은 모두 "모든 키를 한 번에 다루는 일"(리사이즈, 동시 만료, KEYS)이거나 "키마다 붙는 고정 비용"(해시 계산, 객체 메모리)입니다.

### 대책: 샤딩 · 파티셔닝 · 병렬화 · I/O

**샤딩(파티셔닝).** 키를 S개의 독립된 `Store`(샤드)에 나눠 담습니다.

```
shard_id = fnv1a_64(key) >> 56 & (S - 1)     # 해시의 상위 비트로 샤드 선택 (S = 2^k)
                                             # 하위 비트는 샤드 안 버킷 인덱스가 쓰므로 겹치지 않게
store    = shards[shard_id]
store.get(key) / store.set(key, value) …    # 한 키 명령은 샤드 하나로만 감
```

| 항목 | 샤딩 후 | 트레이드오프 |
| --- | --- | --- |
| 리사이즈 지연 | 샤드마다 n/S개만 재해싱 → 최악 지연 약 1/S | 샤드마다 테이블과 리사이즈가 따로 있음 |
| 동시 만료 | 샤드마다 TTL 힙 → 한 번에 다루는 k가 약 1/S | 전체 만료 순서는 샤드 사이에서 보장되지 않음 |
| maxmemory | 샤드마다 `maxmemory / S`, LRU도 샤드 안에서만 | **전체로는 근사 LRU.** 한 샤드에 큰 값이 몰리면 다른 샤드에 여유가 있어도 그 샤드에서 제거됨 |
| DBSIZE / KEYS | 모든 샤드에 보내고 결과를 합침 (fan-out) | 여러 키를 함께 다루는 명령은 비용이 늘고, 샤드 간 원자성이 없음 |
| 확장 | 샤드를 다른 프로세스·서버로 옮길 수 있음 | 샤드 수를 바꾸면 키가 옮겨 가야 함 → Redis Cluster는 고정 16,384개 해시 슬롯(CRC16)을 두고 슬롯 단위로 노드에 배치해, 노드를 늘릴 때 슬롯만 옮김 |

**병렬화.** CPython은 GIL 때문에 스레드를 늘려도 파이썬 코드를 동시에 실행하지 못합니다. 샤드를 **프로세스** 단위로 나누고(샤드마다 `Store` 하나, 프로세스 하나) 앞단 라우터가 `shard_id`로 명령을 보내면 코어 수만큼 처리량이 늘어납니다. 샤드 안에서는 지금처럼 단일 스레드로 실행하므로 O(1)과 불변식이 그대로 유지됩니다(Redis Cluster도 노드마다 단일 스레드). 다른 방법은 해시·리사이즈 같은 뜨거운 경로를 C 확장으로 옮겨 GIL을 풀고 실행하는 것입니다.

**I/O 한계.** 지금 REPL은 표준 입력을 한 줄씩 읽고, 응답 전체를 문자열로 만든 다음 한 번에 출력합니다. 데이터가 커지면 명령 처리보다 입출력이 먼저 병목이 됩니다.

- **큰 응답**: KEYS 10만 개는 2 MB 문자열을 만드는 데만 467 ms가 듭니다. `SCAN cursor COUNT 100`처럼 일부만 돌려주고 "다음에 이어 볼 위치(커서)"를 주면, 명령 하나의 시간과 응답 크기에 상한이 생깁니다. 해시맵의 버킷 번호를 커서로 쓰면 지금 구조로 바로 구현할 수 있습니다(리사이즈 중에도 놓치지 않으려면 Redis의 역비트 커서 방식이 필요).
- **요청마다 왕복**: 실제 서버가 되면 클라이언트가 명령마다 응답을 기다리는 왕복 시간이 처리 시간(µs)보다 훨씬 깁니다. 여러 명령을 한 번에 보내는 **파이프라이닝**과, 소켓 여러 개를 한 스레드에서 다루는 **이벤트 루프**(Linux `epoll`, 파이썬 `selectors`/`asyncio`)가 필요합니다.
- **출력 버퍼**: 응답을 한 번에 만들지 말고 일정 크기씩 나눠 쓰면 큰 응답의 최대 메모리와 첫 바이트까지의 시간이 줄어듭니다.

### 개선 우선순위

| 순서 | 개선 | 기대 효과 (위 측정 기준) | 비용 |
| --- | --- | --- | --- |
| 1 | 만료 처리에 개수·시간 상한 | 대량 만료 시 명령 하나 2,043 ms → 상한(예: 1 ms) 이하. 정확성은 lazy 확인이 보장 | 낮음: `expire_due_keys`에 반복 상한 하나 |
| 2 | `SCAN` 추가 (KEYS 대체) | 명령당 응답을 COUNT 개로 제한 → 467 ms 렌더링이 요청 단위로 쪼개짐 | 낮음~중간: 버킷 번호 커서 |
| 3 | 점진적 리해싱 | 최악 SET 298 ms → 버킷 몇 개 분량(µs). SET 총 시간의 44%가 여러 명령으로 분산 | 높음: 모든 해시맵 연산이 두 테이블을 인식 |
| 4 | 프로세스 단위 샤딩 | 처리량 약 코어 수 배, 리사이즈·만료 최악값 약 1/S | 높음: 라우터, fan-out, 근사 LRU 수용 |
| 5 | 메모리 구조 축소 (근사 LRU, 단일 연결 체인) | 엔트리당 약 575 B 중 LRU 노드 56 B + 버킷 리스트·센티널 약 133 B 절감 (약 3분의 1) | 중간: 정확한 LRU 포기 |
| 6 | 해시 계산 C 확장 | 키당 1.2µs → 수십 ns, GET·SET 모두 빨라짐 | 중간: 과제 제약(직접 구현, 순수 파이썬) 밖 |

1·2는 코드 몇 줄로 꼬리 지연을 크게 줄이므로 가장 먼저 할 일이고, 3·4는 구조를 바꾸는 큰 작업이라 데이터가 실제로 수백만 건 규모가 될 때 의미가 있습니다.
